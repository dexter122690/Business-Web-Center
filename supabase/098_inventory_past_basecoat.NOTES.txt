098 - Past basecoat on released units

Database status 2026-11-26: migration 098 installed in business-web-center after
explicit user action-time approval. The installation guard verified all 74
existing public tables had identical row counts and content hashes before/after.
The session-only verification table had RLS enabled and all public/anon/
authenticated privileges revoked; it was automatically dropped at commit.
No dummy costs were entered in production. Frontend source ships with this file.

Workflow:
Past materials per unit > View materials > Add past basecoat.
Enter quantity (L/mL), total consumed cost and note/reference; Save basecoat.
Existing basecoat becomes Edit past basecoat and is replaced, not added twice.

Scope:
- Only released inventory units in the selected business/branch.
- Existing Inventory edit permission plus existing costing read permission.
- Anonymous users and view-only staff cannot write. No new staff permissions.
- Reuses one basecoat row per unit and existing simple-events audit table.
- Stores note, actor, timestamp and before/after versions in audit history.
- Idempotent request IDs, per-unit lock and expected revision guard retries and
  concurrent edits. Existing released stock/usage write prohibition is unchanged.
- No stock, expenses, invoices, payroll, release dates or historical material
  quantities are changed. Installation only changes functions/execute grants.
- Standard material estimates still use present saved prices. Basecoat uses
  its entered total exactly once, not quantity multiplied by that total.

Validation:
- Full automated suite: 558 passed, 0 failed, 0 skipped.
- Isolated PostgreSQL tested both branches, retry idempotency, stale revisions,
  permission isolation, input validation, audit rollback and migration rerun.
- Isolated browser test: materials 36 + basecoat 600 = 636; edit basecoat to
  700 changes total to 736, with one basecoat line. No live dummy costs entered.
- Reviewed installation wrapper hashes every existing public table before and
  after within the same transaction, aborting on any row change. Wrapper tested
  for success and deliberately introduced row-change rollback in local DB.
